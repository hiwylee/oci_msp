## 1. 빠진 것들 (Critical 누락)

### [Critical] 비즈니스 모델 없음
세 가지 옵션 중 하나를 명확히 선택해야 함:
- **옵션 A**: 내부 생산성 도구 (엔지니어 1인당 관리 테넌시 수가 KPI)
- **옵션 B**: 고객사 포털 과금 SaaS (테넌시당 월정액 or 종량제)
- **옵션 C**: 하이브리드 (내부 도구 → SaaS 전환)

### [High] 테넌시 온보딩 플로우 없음
새 고객사 추가 시 OCI IAM Policy/Dynamic Group/Compartment 설정이 가장 큰 병목.
목표: 15분 이내 온보딩 완료 (5단계 위저드).

### [High] SLA 관리가 Phase 2로 밀려 있음
MSP 사업의 핵심 계약 조건. SLA 기본 설정(티어 정의, 위반 알림)은 MVP에 포함 필요.

### [High] Incident Management 없음
알림 발생 이후 프로세스가 없음:
`Alert 발생 → Incident 생성 → 담당자 배정 → 조치 기록 → RCA → 종료`

### [Medium] 컴플라이언스 정책 없음
감사 로그 보존 기간, 데이터 저장 위치, CSAP/ISO27001 충족 방안 명시 필요.

## 2. MVP 범위 재조정 권고

| 기능 | 현재 | 권고 |
|------|------|------|
| Compute 관리 | MVP | MVP 유지 (핵심) |
| Network 관리 | MVP | MVP에서 조회만, 변경은 Phase 2 |
| Storage 관리 | MVP | MVP에서 조회만 |
| DB 관리 | MVP | Phase 2로 이동 |
| SLA 기본 설정 | Phase 2 | MVP로 당기기 |
| Incident 상태 관리 | Phase 2 | MVP로 당기기 |
| 비용 이상 감지 알림 | Phase 2 | MVP 1.5로 당기기 |

## 3. 현실성 검토 - 위험 요소

1. **OCI API 복잡도 과소 평가**: Rate Limit, Compartment 계층, Cross-tenancy가 예상 2~3배 공수
   - 대응: Week 1~2에 OCI API PoC 진행
2. **멀티 테넌시 Credential 보안 격리**: 복잡도가 높아 늦게 발견하면 리아키텍처 필요
   - 대응: Week 2에 보안 아키텍처 리뷰 확정
3. **실시간 모니터링 파이프라인 복잡도**: OCI Streaming + Celery + Redis 안정화에 예상외 시간 소요
   - 대응: MVP에서는 30초~1분 폴링으로 단순화, Phase 2에서 스트리밍 전환

**현실적 일정**: 실제 고객 적용은 Week 14~16 목표가 적절

## 4. 비즈니스 관점 보완

- 경쟁 구도 분석 추가 필요 (CloudCheckr, Apptio 등 - OCI 미지원 약점 공략)
- 포지셔닝: "OCI 네이티브 MSP 운영 플랫폼 - Compartment/Policy 완전 이해"
- 정량적 ROI 근거: 엔지니어 1명이 테넌시 5~7개 → 15~20개 관리
- 고객사 Read-only 포털을 영업 차별화 포인트로 조기 도입 검토

---

## 5. 기술 보완 사항

- **OCI ATP vs PostgreSQL**: MVP에서는 PostgreSQL on OCI로 시작, 규모 확장 시 ATP 고려
- **관찰 가능성(Observability) 스택 추가**: 플랫폼 자체 모니터링 필요
  - OpenTelemetry + OCI Logging Analytics + OCI APM

---

## 6. UX 보완 사항

- "3클릭 이내" 핵심 작업 TOP 10 정의 및 프로토타입 검증 필요
- 모바일 대응: 최소 알림 확인 + Incident 상태 업데이트
- Empty State / Error State 설계 추가
- 알림 피로도 방지: 그루핑, Maintenance Window, 무음 기능
